# What Terraform detected:
# Running terraform plan after the change showed that the config no
# longer matches reality. The data source that reads the VM's IP from
# multipass info either failed (VM not found) or resolved to a different
# value, causing the null_resource's triggers to differ from state.
# Either way, Terraform reported the discrepancy — which is the essence
# of drift detection.

# Remediation decision:
# We chose to REMEDIATE (restore declared state), not ACCEPT (update
# config to match reality). Reason: the drift was introduced as a
# simulation, not as a deliberate infrastructure change. In a real
# production scenario, if the team had intentionally renamed the VM,
# we would have chosen ACCEPT instead — and updated main.tf to reflect
# the new name, then re-applied to sync state.

# After remediation:
# Reverting main.tf to the original vm_name, and confirming the VM was
# still named "kijanikiosk-payments", produced "No changes" on the next
# plan. Terraform confirmed the config and reality now match.

# Limitation of the Multipass path:
# A null_resource only tracks its explicit triggers (vm_name, vm_ip,
# environment). It does not track attributes of the VM itself like
# instance_type, disk size, or OS version. On a real cloud provider,
# the equivalent resource (aws_instance, google_compute_instance) tracks
# those attributes and would detect drift on any of them. The Multipass
# path teaches the mechanics of drift detection but does not offer the
# same coverage. This is documented as a known limitation of the
# primary path.
