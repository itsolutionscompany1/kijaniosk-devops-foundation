# Tuesday Reflection — Terraform and Multipass

Tuesday's lab required answering four reflection questions on the state file, known-after-apply values, hardcoded vs variable configurations, and what Tuesday's single-server configuration cannot do. The answers below reference the actual configuration and state file created during the lab.

---

## Question 1: The State File as a System

The state file records more about the VM than the configuration declares because **it is the result, not the recipe**. The configuration tells Terraform what should exist. The state file tells Terraform what currently exists — including every attribute the provider returns from the API after creation.

For a Multipass VM this includes the VM's IP address, its storage layout, its network interfaces, and dozens of details that were never in the HCL. Terraform fetches these because the resource type defines them as exported attributes. It writes them into state so that on the next plan it can compare the current reality against the desired state without re-querying the provider for every attribute every time.

When terraform destroy runs, Terraform asks the provider to delete each resource, and after each successful deletion it removes that resource's entry from the state file. The final state after a clean destroy contains no managed resources — exactly what we verified with terraform state list returning empty output.

If the state file were deleted manually without destroying the infrastructure, the next terraform plan would treat the infrastructure as if it never existed. It would show a plan to create resources that are already running, and applying that plan would either duplicate them or fail because the resource names are already taken. The recovery procedure is to either re-import the existing resources (terraform import or, in Terraform 1.5+, an import block) or destroy the infrastructure manually and start fresh.

The lesson: the state file is not a cache — it is the authoritative record of what Terraform owns. Deleting it is destructive.

## Question 2: The (known after apply) Values

(known after apply) appears for any attribute whose value Terraform cannot know until the provider creates or modifies the resource. The provider assigns these values — Terraform simply records whatever comes back.

In this Tuesday configuration, the null_resource.kijanikiosk_api had one such value: its id. Every resource has an id. It is generated when the resource is created and does not exist before. Terraform cannot predict it.

Two example attribute types that would be (known after apply) on a real cloud provider (AWS example):

1. public_ip on an aws_instance — the provider assigns a public IP after the VM is launched. It does not exist before creation.
2. arn on most AWS resources — the Amazon Resource Name is generated by AWS at creation time based on the account, region, and resource path. Terraform cannot compute it.

If an output value depends on a (known after apply) attribute, then during terraform plan that output is also shown as (known after apply). Terraform defers printing the output until after apply completes and the value is knowable. In our case, all five outputs were computable at plan time because they depended only on the data source and literals — so they appeared immediately. If any output referenced null_resource.kijanikiosk_api.id, it would have shown as unknown at plan time.

## Question 3: Hardcoded vs Variable

If the SSH ingress rule hardcodes a specific IP address, the configuration becomes unusable for anyone else on the team — because their IP is different. It also breaks for the original engineer the moment they change networks (a laptop moving between home, office, and mobile hotspot). The configuration would need to be edited for every operator, every environment, every day.

The fix is to declare a variable for the allowed SSH source and let each environment supply its own value:

    variable "ssh_allowed_cidrs" {
      description = "List of CIDR blocks allowed to SSH into the server"
      type        = list(string)
    }

The type is list(string) — a list of strings, because the rule may accept multiple sources (an office network plus a VPN range plus a specific IP for the on-call engineer). AWS security group rules express this as a cidr_blocks argument that takes a list. Multipass's ufw equivalent accepts individual source entries, so the Ansible playbook on Thursday will iterate over the list and add one rule per entry.

This moves the value out of the configuration and into the environment. The same .tf file deploys to staging with one list, and to production with a different list, without changing a single line of the source.

## Question 4: What Tuesday's Configuration Cannot Do

For a production deployment, almost every value in the current configuration would need to change:

- The VM name would need to be kijanikiosk-api-production instead of kijanikiosk-api
- The environment variable would be production instead of staging
- The instance size would be larger — likely more vCPUs and more RAM
- The IP range or subnet would be different, potentially in a different VPC
- The security group rules would be tighter — SSH only from a specific bastion host
- The number of servers would potentially be more than one, since production handles real traffic

Today's approach has one .tf file with hardcoded names and one null_resource. To deploy the same configuration to production, an engineer would have to:

1. Copy the entire directory
2. Rename the resource from kijanikiosk_api to kijanikiosk_api_production
3. Change the VM name in the data source
4. Change all references
5. Maintain two separate directories that drift apart over time

This is exactly the problem Wednesday solves. Modules and for_each let one block of code produce N servers. Variables at the environment level let the same code produce staging and production with different values. And a remote backend lets the team share state so two engineers cannot accidentally apply conflicting changes.

What breaks with today's approach: the moment there is more than one server, or more than one environment, or more than one person running Terraform. All three are true of KijaniKiosk by Thursday.

## Bonus: The Fragile Handoff

One thing this lab exposed that the reflection questions did not directly ask about: the SSH key handoff is fragile.

The course documentation says "Multipass VMs accept SSH from the host machine without additional configuration." In this lab that was not true — the host's ~/.ssh/id_rsa.pub was not in the VM's authorized_keys, and the Terraform remote-exec provisioner failed with SSH authentication failed for the first several apply attempts.

The fix was to inject the public key manually with multipass exec:

    cat ~/.ssh/id_rsa.pub | multipass exec kijanikiosk-api -- bash -c "cat >> /home/ubuntu/.ssh/authorized_keys"

After that, everything worked. But this reveals a real fragility: the pipeline depends on an SSH key being present in the target VM, and Multipass does not guarantee that the host's default key will be the one injected. In a production environment, this would be handled by provisioning the key at VM creation time (Terraform's key_name on the cloud path does exactly this). On the Multipass path, it needs to be an explicit step, not an assumption.

This is exactly the kind of "differs slightly from your test environment" gap the Friday brief asks about. Documenting it here means we catch it before Week 5 builds CI/CD on top of this foundation.
